.. _evs-api--public-api-reference:

Public API reference
====================

The runtime API has four complementary parts. Actions request a change and perform the implementation's validation. State properties report what the mechanic has resolved. Configuration fields describe authored behavior. Events notify consumers about accepted transitions or sampled results. Use the part matching the integration instead of treating every public member as an interchangeable state setter.

All package runtime types use the ``EasyVehicleSystem`` namespace and ``EasyVehicleSystem.Runtime`` assembly. Each topic below lists exact public method signatures, overloads, arguments, return behavior, events/callbacks and declared state/configuration. Base-type links describe inherited package contracts. Unity framework APIs are outside this package reference.

Types and member names are listed alphabetically. Each type shows events/Inspector callbacks first, properties and configuration fields next, and methods and constructors last. Overloads are grouped under their method name.

.. _evs-api--read-a-contract-before-connecting-it:

Read a contract before connecting it
------------------------------------

A bool request result usually answers whether the request was admitted or applied, not whether a later animation has finished. For example, ``PassengerAccess.TryEnter`` starts access, while ``PassengerSeat.TryEnter`` performs immediate occupancy admission. A landing-gear request can be accepted before deployment reaches its endpoint. Each reference specifies the relevant boundary.

Do not infer event delivery from a field edit. A public action can sanitize a value, reject it, update dependent state and publish notifications. Direct configuration writes do not necessarily perform that path. Reapply configuration when changing setup that is copied into native components.

For a replacement, inspect both the method and its event contract. If the base action already publishes success, an override that calls it should not publish a duplicate success. If the replacement omits base behavior, it owns the omitted validation and cleanup as well as the state calculation.

.. _evs-api--event-subscriptions-and-payloads:

Event subscriptions and payloads
--------------------------------

The event tables on each type identify the delegate, trigger and payload. ``Action<int, bool>`` is not self-describing: an index/availability notification and a different boolean state can share a signature. Read the owning type's explanation rather than subscribing by delegate shape alone.

Subscribe to the exact instance whose state the application observes. Keep that source/delegate for unsubscription on disable or handover. Payload snapshots such as ``Telemetry``, ``Impact``, ``LandingEvent`` and ``DamageHit`` can be retained according to their contract; a live Unity ``Collision`` belongs to its callback. A UI can cache telemetry and render it later without reading native physics again.

Inspector ``UnityEvent`` fields appear alongside C# events in their owning type's table. They are separate callback surfaces. Avoid wiring the same gameplay operation to both a supplied commit callback and an Inspector callback unless two invocations are intentional.

.. _evs-api--inheritance-and-reference-scope:

Inheritance and reference scope
-------------------------------

A type section lists members declared there. Follow its package base links for inherited methods/state. The complete method index at the bottom of each technical topic also includes package base contracts, so common ``VehicleModule`` or ``VehicleHandle`` methods remain visible when a subtype declares only one override. Public nested data types and enums are included with their owning topic.

Protected extension hooks are discussed in the relevant :doc:`technical explanation </Scripting/index>` and :doc:`Scripting </Scripting>`. This reference's exhaustive method/event lists cover public runtime declarations; editor authoring utilities and Unity's own inherited lifecycle APIs have separate owners. The supported anatomical authoring entry point is described in :doc:`Anatomical references </API/Anatomy>`.

See :doc:`Units API </API/Units>` for unit-aware configuration and readouts.
